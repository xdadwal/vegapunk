# Milestone 5: Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Someone who has never seen Vegapunk can install it by following the README, run it safely, back it up, upgrade it, find out how to report a security problem, and optionally put a read-only Docker socket proxy in front of it. Nothing is published to a registry.

**Architecture:** Documentation and packaging only, plus one small CLI command and a CI smoke test. Install is "clone, then `docker compose up -d --build`" (the image is built locally). Every command in the docs is run once for real before it is written down. The socket proxy is an optional compose override file, checked by running it.

**Tech Stack:** Docker Compose, Markdown, shell, GitHub Actions; Python (one CLI command).

**Spec:** [`AGENTS.md`](../../AGENTS.md), [`roadmap.md`](roadmap.md) (milestone 5, as narrowed by D1), [`known-issues.md`](../known-issues.md). Builds on M1–M4.

## Decisions made in this plan

| # | Decision | Why |
|---|---|---|
| D1 | **No image is published.** There is no release workflow, no GitHub Container Registry, no `image:` line in `compose.yaml`. Installing means cloning the repository and building. The roadmap row for milestone 5 is rewritten accordingly | The owner said not to publish the image. Publishing can be added later without changing anything else here |
| D2 | A release is a git tag `vX.Y.Z` on `main`, with a `CHANGELOG.md` entry and matching versions in `backend/pyproject.toml` and `frontend/package.json`. `docs/releasing.md` is the checklist. First version: `0.1.0` | Users need to say which version they run and what changed; no registry needed for that |
| D3 | `python -m vegapunk version` prints `Vegapunk <version>` (read from the installed package metadata). Run as `docker exec vegapunk python -m vegapunk version` | Bug reports and upgrade notes need a way to ask the running container |
| D4 | The long guide lives in `docs/install.md` (install, configuration, data and backups, upgrading, uninstalling, troubleshooting). `README.md` keeps a short quick start and links to it | AGENTS.md: README is user-facing and brief |
| D5 | **Backups are taken with the container stopped**: stop, archive the volume with a throwaway container, start. Restore is the reverse into an empty volume. The guide says the data folder holds `vegapunk.db`, `conversations.db` and `secret.key`, and that a backup without `secret.key` cannot decrypt the saved API key | SQLite runs in WAL mode, so copying live files can lose recent writes; stopping is the simplest correct method |
| D6 | **Upgrading** is: back up, `git pull`, `docker compose up -d --build`. Migrations run at start. Going back means restoring the backup, because a database written by a newer version is refused at start | Matches the existing behaviour (AGENTS.md "Startup refuses a database written by a newer version") |
| D7 | The optional socket proxy is `compose.socket-proxy.yaml`, an override used as `docker compose -f compose.yaml -f compose.socket-proxy.yaml up -d --build`. It runs `tecnativa/docker-socket-proxy` (pinned to a version tag, verified to exist) with only the read endpoints Vegapunk uses enabled (containers, info, version; no POST), and points Vegapunk at it with `VEGAPUNK_DOCKER_URL`, with the real socket no longer mounted into Vegapunk. A third-party image is acceptable here because it is optional and documented, not a dependency | The roadmap asks for it; it gives a hard read-only guarantee that the mount flags cannot |
| D8 | A script `scripts/smoke.sh` builds the image, starts it on a free port under a throwaway project name, waits for healthy, checks `/api/health` and `/api/setup/status`, and always cleans up. CI's docker job runs it and `docker compose config -q` for both compose files | Today CI only builds the image; a container that builds but does not start would pass |
| D9 | `SECURITY.md` says: report privately through GitHub's "Report a vulnerability" (the owner must switch private vulnerability reporting on in the repository settings; the plan lists it as an owner action); only the latest release is supported; what Vegapunk protects and does not (single admin, the Docker socket is full control of Docker, the agent only reads, API key encryption's limits, redaction is best effort, sign-in is rate limited server-wide, no HTTPS of its own); the recommended deployment (not on the open internet, behind an HTTPS proxy with `VEGAPUNK_SECURE_COOKIES=1`) | Honest scope; every claim is checked against the code |
| D10 | The docs state what has and has not been verified: run on Docker Desktop (macOS); Linux is the supported target but has not been run by the author; no hosted AI provider has been tried; the one local model tried is Gemma through Docker Model Runner | The known-issues file already says this; a user should not have to find it there |

## Global Constraints

- **Every command shown in a doc was run** (or is marked "not verified" in the text). The implementer records each in the task report with its output.
- No secrets, personal paths, host names or e-mail addresses in any committed file.
- Do not publish anything and do not add an `image:` line, a registry login, or a release workflow (D1).
- README stays brief; detail goes in `docs/`. UI wording rules do not apply to docs, but the docs say "agent", not "AI", for the operator and keep "AI provider" for settings.
- New dependencies: none in the app. The proxy image is optional and only in the override file.
- Backend: `uv run ruff check .`, `uv run ruff format --check .`, `uv run pytest`. Frontend unchanged unless a task says so. Format only files you changed. Commit after each task; do not push unless asked.

## Review Focus

1. **A documented command that does not work** (wrong volume name, a flag that differs between Docker Desktop and Linux, `stat -c` on macOS, Compose version differences): each must have been run; Linux-only ones are labelled. [Tasks 3, 4]
2. **The proxy is not really read-only or breaks capture:** a write through it (`POST /containers/<id>/stop`) must be refused; capture, container stats and logs must still work through it. [Task 2]
3. **Backups that restore into a broken install:** a restored volume must start, show the same admin and findings, and the saved AI key must still decrypt (needs `secret.key`). [Task 3]
4. **Upgrade from today's volume:** an existing M1–M4 data volume must start under the release build without manual steps. [Task 3]
5. **A SECURITY.md that overclaims:** every statement about encryption, redaction, rate limiting and what the agent can do must match the code. [Task 4]

### Task 2: The socket proxy override

**Files:** Create `compose.socket-proxy.yaml`, `docs/socket-proxy.md`.

**Interfaces:** Produces a working override and the exact commands to use it.

- [ ] **Step 1: Find what Vegapunk calls.** From `backend/vegapunk/host/docker.py` and the docker SDK usage list every Docker API endpoint used (ping, info, version, container list and inspect, one-shot stats, logs). Check which `tecnativa/docker-socket-proxy` settings allow exactly those and nothing else, and the latest stable version tag (verify it exists with `docker pull`). Record the table in the task report.
- [ ] **Step 2: Write the override.** `socket-proxy` service (pinned tag, read-only root filesystem if it works, socket mounted `:ro`, no published ports, environment enabling only what step 1 found and `POST=0`), and on `vegapunk`: `VEGAPUNK_DOCKER_URL=tcp://socket-proxy:2375`, the socket volume and `group_add` removed (use Compose's `!override`/`!reset` tags; state the minimum Compose version in the doc and verify it against the installed one), `depends_on` the proxy. The vegapunk data volume keeps the same name so switching does not lose data.
- [ ] **Step 3: Verify for real** with a throwaway project name and a different host port (so the owner's running instance is untouched): bring it up, wait healthy, create the admin through the API, confirm `GET /api/host` and `GET /api/containers` show real data, confirm container stats and logs work (open a container's detail through the API, or run an agent tool path via the existing tests' fake — prefer real HTTP calls), then from inside the Vegapunk container try a write through the proxy (`POST http://socket-proxy:2375/containers/<id>/stop` and `/restart`, and a `DELETE`) and show each is refused (403 or similar), and show that a container named in the test is unchanged. Tear everything down (`down -v` for the throwaway project only). Record commands and outputs.
- [ ] **Step 4: Write `docs/socket-proxy.md`:** why (the socket is full control of Docker whatever the mount flags say), what the proxy changes and what it does not (it narrows Docker API access to reads; Vegapunk itself already only reads), how to enable and disable it, how to check it is working (the exact write-refused command), the third-party image caveat and pin, Linux vs Docker Desktop notes (as verified), troubleshooting (the page says it can't read Docker: check the proxy logs).
- [ ] **Step 5: Commit** `Add an optional Docker socket proxy`.
