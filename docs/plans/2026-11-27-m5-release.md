# Milestone 5: Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Someone who has never seen Vegapunk can install it by following the README, run it safely, back it up, upgrade it, find out how to report a security problem, and optionally put a read-only Docker socket proxy in front of it. Nothing is published to a registry.

**Architecture:** Documentation and packaging only, plus one small CLI command and a CI smoke test. Install is "clone, then `docker compose up -d --build`" (the image is built locally). Every command in the docs is run once for real before it is written down. The socket proxy is an optional compose override file, checked by running it.

**Tech Stack:** Docker Compose, Markdown, shell, GitHub Actions; Python (one CLI command).

**Spec:** [`AGENTS.md`](../../AGENTS.md), [`roadmap.md`](roadmap.md) (milestone 5, as narrowed by D1), [`known-issues.md`](../known-issues.md). Builds on M1–M4.

## Decisions made in this plan

| # | Decision | Why |
|---|---|---|
| D1 | **No image is published.** There is no release workflow, no GitHub Container Registry, no `image:` line in `compose.yaml`. Installing means cloning the repository and building. The roadmap row for milestone 5 is rewritten accordingly | The owner said not to publish the image. Publishing can be added later without changing anything else here |
| D2 | A release is a git tag `vX.Y.Z` on `main`, with a `CHANGELOG.md` entry and matching versions in `backend/pyproject.toml` and `frontend/package.json`. `docs/releasing.md` is the checklist, including two owner actions the checklist cannot do: merge the whole M1–M5 stack into `main` (it holds only the scaffold today) and push the tag (AGENTS.md: nothing is pushed unless asked). First version: `0.1.0` (`backend/pyproject.toml` already says it; only `frontend/package.json`, now `0.0.0`, changes) | Users need to say which version they run and what changed; no registry needed for that |
| D3 | `python -m vegapunk version` prints `Vegapunk <version>` (read from the installed package metadata). Run as `docker exec vegapunk python -m vegapunk version` | Bug reports and upgrade notes need a way to ask the running container |
| D4 | The long guide lives in `docs/install.md` (install, configuration, data and backups, upgrading, uninstalling, troubleshooting). `README.md` keeps a short quick start and links to it | AGENTS.md: README is user-facing and brief |
| D5 | **Backups are taken with the container stopped**: stop, archive `/data` with a throwaway container (`tar -C /data -cpf - .`, which keeps ownership), start. The volume name is not fixed (it is `<project>_vegapunk-data`, and the project is the clone's folder name), so the guide finds it with `docker inspect vegapunk --format '{{range .Mounts}}{{if eq .Destination "/data"}}{{.Name}}{{end}}{{end}}'`. Restore is the reverse into an empty volume, run as root with `--same-owner`, followed by an explicit `chown -R 10001 /data` (the app runs as uid 10001 and cannot write a root-owned volume). The guide says the data folder holds `vegapunk.db`, `conversations.db` and `secret.key`, and that a backup without `secret.key` starts fine but the saved API key is lost, because a missing key file is silently regenerated at start | SQLite runs in WAL mode, so copying live files can lose recent writes; stopping is the simplest correct method |
| D6 | **Upgrading** is: back up, `git pull`, `docker compose up -d --build`. Migrations run at start. Going back means restoring the backup, because a database written by a newer version is refused at start (with `restart: unless-stopped` that shows as a restart loop; troubleshooting says to read `docker compose logs vegapunk` for "written by a newer Vegapunk") | Matches the existing behaviour (AGENTS.md "Startup refuses a database written by a newer version") |
| D7 | The optional socket proxy is `compose.socket-proxy.yaml`, an override used as `docker compose -f compose.yaml -f compose.socket-proxy.yaml up -d --build`. It runs `tecnativa/docker-socket-proxy` (pinned to a version tag, verified to exist) with exactly these settings: `PING=1` (`/_ping`), `VERSION=1` (the Docker SDK calls `GET /version` while building the client, so it is required), `INFO=1`, `CONTAINERS=1` (list, inspect, stats, logs), `EVENTS=0` (on by default, unused) and `POST=0` (this denies every method except GET and HEAD, so DELETE too). The guide notes that `CONTAINERS=1` also allows reading container files through the archive endpoint. Compose's `!override`/`!reset` tags need Compose 2.24.4 or newer (the guide says so); the override uses `!override` on `volumes` keeping the `vegapunk-data:/data` mount (a bare `!reset` would drop it) and `!reset` on `group_add`, and points Vegapunk at it with `VEGAPUNK_DOCKER_URL`, with the real socket no longer mounted into Vegapunk. A third-party image is acceptable here because it is optional and documented, not a dependency | The roadmap asks for it; it gives a hard read-only guarantee that the mount flags cannot |
| D8 | A script `scripts/smoke.sh` builds the image, starts it on a free port under a throwaway project name, waits for healthy, checks `/api/health` and `/api/setup/status`, and always cleans up. CI's docker job runs it and `docker compose config -q` for both compose files | Today CI only builds the image; a container that builds but does not start would pass |
| D11 | `compose.yaml` gets a configurable port, `"${VEGAPUNK_PORT:-8000}:8000"`, and keeps `container_name: vegapunk` (existing installs and the guide's `docker exec vegapunk …` keep working). Because `-p <project>` does not isolate a hardcoded container name or port, `scripts/smoke.sh`, the proxy check and the upgrade check run with a small override (`scripts/smoke.override.yaml`: `container_name: !reset null`, port from `VEGAPUNK_PORT`) so they never touch a running `vegapunk` | Verified by the plan review: without this every throwaway run collides with the owner's instance |
| D12 | The image has no `curl` or `wget`; checks run from inside it use `python -c "import urllib.request …"`, and a 403 from the proxy is the expected answer to a write | Reviewed: `docker exec vegapunk sh -c 'which curl wget'` finds neither |
| D9 | `SECURITY.md` says: report privately through GitHub's "Report a vulnerability" (the owner must switch private vulnerability reporting on in the repository settings: `gh api repos/xdadwal/vegapunk/private-vulnerability-reporting` reports `{"enabled":false}` today, so `SECURITY.md` must not be merged until it reports `true`); only the latest release is supported; what Vegapunk protects and does not (single admin, the Docker socket is full control of Docker, the agent only reads, API key encryption's limits, redaction is best effort, sign-in has a server-wide lockout (5 failures within 15 minutes lock sign-in for 15 minutes), cookies are `HttpOnly`, `SameSite=Lax` and `Secure` only with `VEGAPUNK_SECURE_COOKIES=1`, passwords use argon2, body-less POSTs need `X-Requested-With: vegapunk`, a missing `secret.key` is regenerated silently, no HTTPS of its own); the recommended deployment (not on the open internet, behind an HTTPS proxy with `VEGAPUNK_SECURE_COOKIES=1`) | Honest scope; every claim is checked against the code |
| D10 | The docs state what has and has not been verified: run on Docker Desktop (macOS); Linux is the supported target but has not been run by the author; no hosted AI provider has been tried; the one local model tried is Gemma through Docker Model Runner | The known-issues file already says this; a user should not have to find it there |

## Global Constraints

- **Every command shown in a doc was run** (or is marked "not verified" in the text). The implementer records each in the task report with its output.
- No secrets, personal paths, host names or e-mail addresses in any committed file.
- Do not publish anything and do not add an `image:` line, a registry login, or a release workflow (D1).
- README stays brief; detail goes in `docs/`. UI wording rules do not apply to docs, but the docs say "agent", not "AI", for the operator and keep "AI provider" for settings.
- New dependencies: none in the app. The proxy image is optional and only in the override file.
- Backend: `uv run ruff check .`, `uv run ruff format --check .`, `uv run pytest`. Frontend unchanged unless a task says so. Format only files you changed. Commit after each task; do not push unless asked.

## Review Focus

1. **A documented command that does not work** (wrong volume name, a flag that differs between Docker Desktop and Linux, `stat -c` on macOS, Compose version differences): each must have been run; Linux-only ones are labelled. [Tasks 3, 4]
2. **The proxy is not really read-only or breaks capture:** a write through it (`POST /containers/<id>/stop`) must be refused; capture, container stats and logs must still work through it. [Task 2]
3. **Backups that restore into a broken install:** a restored volume must start, show the same admin and findings, and the saved AI key must still decrypt (needs `secret.key`). [Task 3]
4. **Upgrade from today's volume:** an existing M1–M4 data volume must start under the release build without manual steps. [Task 3]
5b. **Throwaway runs colliding with the running instance** (hardcoded container name and port 8000, no `curl` in the image, the 30 s health interval): every check uses the override and polls `docker inspect` health. [Tasks 2, 3]
5. **A SECURITY.md that overclaims:** every statement about encryption, redaction, rate limiting and what the agent can do must match the code. [Task 4]
